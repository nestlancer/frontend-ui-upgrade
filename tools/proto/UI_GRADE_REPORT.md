# Prototype UI grade report — screenshot vs. proto HTML

**Scope:** every screenshot in `screenshot-manifest.csv` (181 files: 119 admin, 45 client, 17 public) compared with the proto HTML page built into `proto/` by `tools/proto/build.mjs`. **Target grade: A (≥90).** The current screenshot UI is graded **C** by the team; this report grades the proto pages against the same screens.

## 1. Headline

- **4 of 181 screens reach A.** B: 13, C: 20, D: 92, F: 52.
- Median score: **62.8** (target 90). Median content coverage against the audit notes is **36%**, so the main gap is content and states, followed by mobile layout and health.
- Main systemic gaps: text under 11px (181), overflows at 390px (not responsive) (177), few section headings (171), content coverage under 60% (151), page length differs >40% (80), state not built as own page (59).
- The 4 A grades are: public login, public pricing, public register and the admin dashboard. Operator console and client detail screens are mostly D or F.

## 3. Scoring method

Score = 0.50 × **Fidelity** + 0.30 × **Health** + 0.20 × **UX**.

- **Fidelity (0–100):** content coverage ×70 — share of distinctive words and amounts recorded for that screenshot in `tools/proto/DATA_AUDIT.md` that appear in the rendered proto text; page-length match ×15; ink-density match ×15 (top 1440×900 viewport). Screens with no audit notes are capped.
- **Health (0–100):** starts at 100; −15 per page error, −5 per console error (network-only failures from the sandbox are excluded), −10 broken images, −10 desktop overflow, −10 overflow at 390px, −10 placeholder text (`NaN`, `undefined`, `lorem`, `TODO`), −5 text under 11px, −5 missing title or h1, −2 missing description.
- **UX / assumptions (0–100):** primary action present +25; ≥3 nav links +20; breadcrumb or public page +15; ≥2 section headings +15; form or table present +10; theme/FAB switcher +10.
- **Cap:** a screen whose own state (dialog, tab, detail) has no proto page is graded against the nearest page and capped below A (89.9). An A therefore requires the exact screen to exist in the proto.
- Pixel layout correlation was measured but **not scored**: the proto uses a different grid and fonts from the captured app, so pixel-level correlation penalises reflow rather than fidelity. It is kept in `scores2.json` for reference.
- **Limitations:** the content check is only as good as the audit notes; the sandbox could not load Google Fonts, so typography in both renders falls back to system fonts; visual judgement (colour, polish, spacing) still needs a human review — use the review column in Section 5.

| no h1 | 1 | Give the page one h1 with the screen title. |
